## Implementación

`@supabase/supabase-js` 2.119.0 por npm/pnpm, versión consultada en el registro oficial. Solo URL y publishable key en frontend. `signUp` inserta id/nombre en perfiles; el inicio y la recarga leen ese registro bajo RLS. Si el registro se interrumpe, puede recuperar exclusivamente su propio perfil con su metadata autenticada. Las contraseñas se envían solo a Supabase Auth; no se almacenan en archivos, tabla perfiles ni logs. La sesión se conserva con el cliente estándar. El estado fiscal de demostración se limpia al cambiar usuario o cerrar sesión.

La cuenta y el nombre son persistentes y reales; tickets, facturas y declaraciones de esta versión continúan siendo demostración. El backend privado de Sites no se publica ni se conecta a esta nueva identidad.

## Problemas y resolución

- GitHub no tenía el código de la demo: se agregó el frontend actual bajo vercel-app en una rama, conservando la landing.
- Ya había una identidad ChatGPT en Sites: se limitó Supabase a la versión de Vercel aprobada; no se migraron datos ni se cambió esa identidad.
- Confirm email activado: se apagó con aprobación expresa para esta clase.
- Subida por la extensión requiere acceso a archivos locales: se utilizó el selector nativo de Chrome, sin ampliar permisos.
- Revisión automática rechazó guardar credenciales ficticias en un JSON: no se guardaron contraseñas; las pruebas adicionales usaron clientes sin persistencia.
- El cliente de verificación restringido no tenía red: la comprobación RLS se ejecutó con acceso de red autorizado, sin claves secretas.
- La consola de los casos de error contiene respuestas 400 esperadas; los formularios muestran el mensaje correspondiente y no conceden acceso.
